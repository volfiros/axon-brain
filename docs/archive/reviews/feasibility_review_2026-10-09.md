**Verdict: the core product is feasible, but the complete proposed demo is not a credible 48-hour commitment from this starting point.** Build a scoped incident assistant that retrieves evidence, produces a cited brief, and demonstrates one approved sandbox restoration. Treat broad branch verification, automatic association, and production operation as separate increments.

This review covers the current master design, shared specifications, all eight phase plans, SRE requirements/schema/integration plan, resource plan, revision record, archived original, and both background PDFs. The workspace contains design documents, with no application implementation or executable acceptance suite. Provider documentation was checked for the main integration assumptions; no authenticated provider calls, database crash tests, model benchmarks, or sandbox actions were run. Findings below are design analysis, not observed runtime defects. Existing design files have not been changed.

The revised Markdown correctly rejects several stronger claims in the older material: typed output does not guarantee truth; ancestry is not behavioral validation; customer reachability is not measured failure; and source revert differs from deployment rollback. Preserve these corrections.

Within 48 hours, commit only to a narrow vertical demonstration with prepared data/access. The current full gate should remain incomplete when its required checks are missing. **Priority findings and changes needed before implementation**

1. **High — The critical data-maintenance workflow is postponed, although the product depends on it immediately.** The [source adapter contract](../design/source_adapters.md) requires a verified manifest for dependencies, repository bindings, delivery groups, revision effects and document links. SRE conclusions similarly depend on authoritative build, catalog and customer mappings. Ingestion can normalize these records; it cannot manufacture their missing meaning. Clef suggestions explicitly cannot supply delivery proof. The result can therefore be technically correct but frequently unable to answer outside curated fixtures. Define who confirms each mapping, the confirmation UI or CLI, version/expiry rules, conflict handling and the trigger for revalidation after a task or delivery changes. Measure answerable-query coverage and operator maintenance time on a small real sample before building more model routing.

2. **High — Query-time association persistence can invalidate its own response.** [Association step 8](../design/task_branch_association.md) requires persistence through the import protocol. That protocol increments the graph generation, while the [final read gate](../design/phase_01_graph_and_fixtures.md) rejects a response assembled from the preceding generation. A straightforward implementation would infer at generation G, publish its candidate at G+1, invalidate itself, and potentially repeat until the retry budget is exhausted. The documents do not specify when this write occurs or how a retry avoids it. Return request-local suggestions without changing the canonical graph during the query; retain their audit records separately and project them later through controlled ingestion. Alternatively specify a separate version for derived suggestions. Add a regression requiring successful discovery to finish without a self-triggered generation retry.

3. **High — Known access revocation has no independent invalidation mechanism.** The [adapter contract](../design/source_adapters.md) both aborts required-source imports before graph mutation and requires revoked content to become unavailable. A Google Docs 403 can therefore leave the previous READY snapshot and its content intact. The intended access rule is correct, but its implementation cannot depend on a successful new snapshot. Add a durable source-access denial/authorization version outside the projection and consult it during retrieval, trace access and final response publication. Do not equate a 403/404 with deletion. Test revocation during a failed import and while an answer model is running; a still-valid graph generation must not release the revoked text.

4. **High for a live incident service — Full rebuilds conflict with frequent event ingestion.** [Phase 1](../design/phase_01_graph_and_fixtures.md) rebuilds the managed projection and blocks reads; [the SRE plan](../design/sre_integration_plan.md) routes accepted-event graph changes through this protocol. Under repeated updates, briefs can be rejected at admission or repeatedly invalidated during model calls. This is a valid consistency-first demo tradeoff, already acknowledged in the documents, but there is no batching policy, ingestion-load envelope or answer-availability target. Keep durable receipts independent, batch/coalesce projection updates, deduplicate before rebuilding, and specify a bounded publication cadence. Measure blocked-read fraction and restart time at the intended event rate. A later immutable-generation or transactional incremental design needs its own validation; do not remove the dirty-state protection to gain availability.

5. **High before sandbox execution — The action interfaces exist, but the execution protocol and compatibility source remain underspecified.** [ActionPlan](../design/contracts.md) usefully includes approval, versions, idempotency and UNKNOWN_OUTCOME. The [sandbox gate](../design/sre_integration_plan.md) does not yet select the runtime, operation, compatibility manifest or recovery measurements. Choose one disposable workload and a declarative restore-to-artifact operation. Define legal state transitions, an atomic approval-to-running claim, a durable operation ID, and reconciliation after a crash between target mutation and receipt storage. A local lock alone cannot stop an external deploy between recheck and mutation: use a target-side conditional update where supported, or explicitly make the sandbox single-writer. Define schema/config compatibility as versioned evidence, plus a concrete recovery window, sample count and failure threshold. Test the crash window and changed-target variant, not merely duplicate HTTP requests.

6. **Medium–high — There is no end-to-end source-call and latency budget.** [Discovery](../design/task_branch_association.md) permits inspecting up to 20 branches and 1,000 commits per branch, plus changed-file evidence. That is up to 20,000 branch/commit memberships, not necessarily unique commits or API calls. Without deduplication and local indexing, file-detail calls can dominate runtime. The 60-second evidence TTL is difficult to reconcile with a cold scan, activity reconstruction, decision calls, an answer call and final checks. Use a shared local Git object/metadata cache keyed by SHA, fetch history in background, and keep query-time source reads small. Add per-source request quotas, concurrency limits and one overall deadline. Separate warm-context targets from cold synchronization. Plane documents 60 requests/minute per API key; GitHub's common authenticated limit is 5,000/hour, with additional secondary limits. [Plane rate limits](https://developers.plane.so/api-reference/introduction), [GitHub rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).

7. **Medium — Incident clarification cannot be represented by the shared continuation contract.** [QueryRequest and clarification](../design/contracts.md) accept only task, repository and branch selections, while SRE resolution can require choosing a service, instance, region or incident window. ASK_FOR_HELP has no corresponding typed continuation here. Add service/instance clarification with the same principal/scope/version binding, or explicitly define a separate incident continuation endpoint. Also define how a clarification resumes a durable investigation job.

8. **Medium — Temporal records need correction and conflict rules.** The [SRE schema](../design/sre_graph_schema.md) correctly separates validity from recorded time. It does not fully specify late-arriving deployments, corrected interval boundaries, simultaneous on-call overrides, provider clock disagreement or ordering of conflicting lifecycle events. Define source precedence, per-record revisions, interval overlap rules and whether a history query means “best current reconstruction” or “what was known then.” Test an event received after a brief that changes the inferred active deployment. Preserve the earlier brief as an observation of earlier knowledge.

9. **Medium — Narrative grounding is a stated requirement, not a general mechanical guarantee.** [Phase 5](../design/phase_05_context_and_llm_answers.md) already acknowledges that valid citations do not establish entailment. Specify which claim types can be checked deterministically, and keep targets, impact classifications, state transitions and commands in engine-rendered fields. For procedural guidance, prefer source excerpts or constrained paraphrases with their prerequisites. Test unsupported claims that cite real evidence IDs. A second model can help evaluate support, but it is another probabilistic check with cost and latency, not a proof of correctness.

10. **Medium — The model experiment needs a narrower first question and a real-data coverage measure.** Mandatory incident checks are already deterministic, so the specialized model's value is largely optional exploration order and ambiguous candidate selection. Begin with one accessible provider and compare useful-evidence recall, cost and time against direct retrieval. The proposed synthetic sets are reasonable smoke tests; the documents correctly avoid production reliability claims. Add a small consented real-data set with missing mappings and measure retrieval recall separately from model accuracy. Do not spend the first sprint evaluating every provider or tuning multiple independent probabilistic judgments before the basic product works. See [model evaluation](../design/decision_models.md).

**Additional implementation decisions to settle.** Make GitHub authentication, permission scope, API version and aggregate current-review policy as explicit as Plane/Docs. Define source-specific freshness for runbooks, review state, on-call and deployments; a stable Git head alone does not refresh those facts. Specify exactly one demo application writer and how scripts, the investigation worker and MCP pass through the same gate. The official MCP server's default read-only flag is overridable per query, so the proposed gateway must enforce its allowlist; separate least-privilege database credentials provide an additional boundary. [Official MCP behavior](https://github.com/FalkorDB/FalkorDB-MCPServer#read-only-mode-for-replica-instances).

There is minor document drift: the master repeats the association paragraph, table row and success criterion. More importantly, the SRE path calls branch revision effects mandatory while the resource plan calls branching an optional second example. Publish a requirement-to-release matrix so implementers know which development gates actually apply to an incident-only demo. Resolve this explicitly rather than silently dropping requirements.

**Recommended implementation order.** First prove container persistence and one read from each required live provider, plus one Clef and answer-model call. In parallel as a planning activity, inventory a handful of real tasks/services and identify who owns missing mappings. No need to complete three full connectors to discover that a critical account or data field is unavailable.

Then build one incident slice: replay an alert; retrieve historical deployment, current responder, runbook and customer evidence; show a cited brief and actual graph trace; produce one version-bound recovery proposal. Add a blocked schema-compatibility variant before adding execution. Implement the durable sandbox executor and recovery checks next, followed by required live task/document/code context. Retain the existing strict gates as acceptance work, with an explicit release boundary.

Defer ID-free branch discovery, the full revert/reapplication matrix, additional model providers, GraphRAG SDK, native algorithm experiments and advanced visualization from that first incident release. These remain feasible later increments; changing their current mandatory status requires a documented scope revision.

The strongest product claim to pursue is: **“We assemble the evidence an engineer needs to investigate and approve a specific recovery action.”** Demonstrate that changing the evidence changes the proposed action. Measure answer coverage, supported claims, time to a useful brief, and operator effort maintaining the graph. Those results will establish practical value more convincingly than graph size or hop count.
