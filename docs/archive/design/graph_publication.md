# Graph publication, event batching and scoped validation

Status: proposed, 2026-10-09. This specification fixes the reviewed ingestion, answer-publication and clarification risks. It extends [contracts](contracts.md) and the [Phase 1 recovery protocol](phase_01_graph_and_fixtures.md#snapshot-consistency); application implementation and runtime validation remain future work.

## Projection ownership

Keep one shared FalkorDB graph and canonical entity IDs so incident paths still join directly to tasks, commits and runbooks. Partition its managed records into two logical projections with separate durable `ImportState` records and read/write gates:

- `STRUCTURAL`: tasks, epics, repositories, branches, commits, reviews, document references, verified mappings and the service/directory/customer catalog.
- `INCIDENT`: alerts, incident lifecycle projections, deployments, artifacts, runtime changes, observations, effective on-call assignments and projected action records. These are derived from the retained incident event log.

Every managed node/edge has immutable `projection_owner`. A relationship belongs to INCIDENT when it originates in an incident-owned record, including its links to structural entities; other relationships belong to STRUCTURAL. Versioned catalog dependencies and customer routing remain structural; runtime observations do not overwrite catalog fields. Current runtime state comes from incident evidence rather than mutating the catalog's `ServiceInstance` identity. Validate ownership before writes. A template declares all projections it reads, including cross-projection joins, and reads only their READY snapshots.

Retain canonical structural endpoints referenced by incident records, tombstoning them when authoritative removal requires it. A structural rebuild must preserve incident-owned nodes/edges and cannot delete an endpoint with retained incident links. Historical retrieval labels tombstoned endpoints; current decisions exclude them and report coverage gaps. Changes affecting both owners require a coordinated operator import, never a webhook-induced structural rebuild.

An active owner bundle describes the complete logical projection, including unchanged records. Record `snapshot_id` denotes its last materialization and can predate that bundle after a delta; do not filter current records by equality with the active snapshot ID. READY plus validated bundle membership/coverage establishes the current view. Fingerprints exclude this materialization metadata while evidence preserves its originating read tokens and observation times.

One application worker serializes publication. Acquire gates in STRUCTURAL, INCIDENT order, then the access-registry gate if needed; no reverse acquisition. Incident publication holds the structural shared gate to validate endpoints and its own exclusive gate. Structural rebuild/recovery holds both exclusive gates to protect cross-projection links, but changes only its owned records/state unless explicitly performing a coordinated import. A multi-projection publication marks every affected projection DIRTY before mutation and admits readers only after all required projections are durably READY. A failed incident update blocks incident-backed reads; structural-only queries remain available. Structural recovery blocks both kinds of read. Direct, MCP, picker, cache and trace routes use these same declarations/gates.

## Durable incident batching

`POST /webhooks/{provider}` authenticates and atomically persists the deduplicated event, receipt and durable pending-job reference before returning 202. Operator lifecycle events and action receipts use the same retained log. The graph is a projection; acceptance never waits for projection publication or inference. Duplicate deliveries return the original receipt and do not schedule new graph work.

Use a configurable `EventBatchPolicy`: `window_seconds=30` (allowed 15-30), `min_read_interval_seconds=15`, and bounded `max_batch_events`/`max_pending_events` recorded in startup configuration. The window starts at the oldest unprojected accepted event and is fixed: later arrivals cannot keep extending it. Coalesce redundant projection updates by tenant, subject and source revision; retain every distinct audit/lifecycle event. Ordering follows source revision/effective-time rules, with conflicts preserved rather than last-received-wins guesses.

The worker closes a batch at its deadline or event-count cap. Publish at most one incident batch per configured window and leave at least `min_read_interval_seconds` of READY time after each publication before the next normal batch. Reaching the cap queues another bounded batch, not an immediate chain of rebuilds. Events arriving during preparation/publication belong to the next batch. An empty or semantically unchanged batch advances its durable projected position without changing graph generation or semantic fingerprints. Recovery and explicit operator imports may override normal cadence; record that reason.

Prepare a validated immutable full INCIDENT rebuild bundle plus an idempotent affected-record delta and the exact consumed log position before mutation. Under the projection gates, persist INCIDENT DIRTY and its new generation/pending bundle before applying the delta. Update only incident-owned records; do not rebuild the structural projection. Validate endpoint identities, affected records and scope/coverage metadata, then durably publish INCIDENT READY and its snapshot. After that acknowledgment, mark the batch consumed in retained storage. A crash between graph publication and log-position acknowledgment reconciles the published bundle position before replay, so it cannot duplicate effects. A crash during mutation leaves INCIDENT DIRTY; recover by rebuilding only INCIDENT from its retained full bundle, preserving STRUCTURAL.

In-memory timers and grouping indexes are disposable accelerators. Restart reconstructs pending windows from durable event positions and timestamps; missing memory never loses an accepted event. Persist publication time so restart cannot bypass the read interval. When a pre-acceptance pending limit is reached, return retryable 503 `EVENT_BACKLOG_FULL` without an acceptance receipt; previously accepted events remain retained. Expose accepted/projected positions, oldest pending age, batch size, rebuild/delta time, blocked-read fraction and relevant/unrelated answer retries. Pending events are disclosed as unprojected coverage, not silently treated as graph evidence. Do not label a brief current when required observations exceed their configured freshness limit. Measure the backlog/freshness envelope before enabling a real stream; the cadence is not a production availability guarantee.

An incident answer states the published log position/time it covers. Attach current accepted/projected positions and pending age as engine-rendered response metadata; accepting an unprojected event alone does not invalidate otherwise equivalent published facts or manufacture knowledge of that event. If relevant events remain pending, label the brief as covering the published position, not all accepted observations. Execution prerequisites require relevant pending updates to be projected/reconciled and actual target state checked before mutation. Long-running action probes/provider calls run as nonblocking tasks in the single application process; they cannot suspend the event-publication scheduler. All graph writes still share its serialized writer.

## Request read set

`GraphReadSet` captures the inputs actually used by resolution, traversal, decisions, association inference and answer construction:

- Per-projection original `(generation, active_snapshot_id)` tokens.
- Every approved template ID/version, exact scoped parameters and fixed query-time reference timestamps; canonical semantic result hash and coverage/completeness hash.
- Entity and relationship IDs, source versions, values/qualifiers, adjacency membership, document hashes/anchors, mapping/effect/policy/identity versions and original freshness deadlines.
- Exact relevant candidate/stable Git heads and source-resource/enclosing-scope access versions.

A template fingerprint includes all rows and relationship evidence within its declared bound, not just nodes cited by the LLM. Hash empty results with the full lookup scope and authoritative coverage; hash aggregate membership/counts and eligibility rules. A newly added prerequisite, epic child, delivery effect, deployment or matching candidate must change the relevant read result even if every previously cited node is unchanged. Include observation times that support a claim, but exclude transport-only metadata such as projection generation, snapshot ID and ingestion time. Use canonical ordering and application IDs, never internal numeric IDs or incidental row order. Overflow, restricted/incomplete critical coverage, unsupported templates or missing fingerprints cannot establish equivalence.

Historical queries keep their requested event-time window fixed. Current-state facts additionally expire at the earlier of their source TTL and a known effective-interval boundary, such as the end of an on-call assignment. Crossing that boundary requires a current-time lookup even without any publication/generation change; replaying an old timestamp cannot establish a current responder or deployment. Unknown temporal coverage remains an explicit limitation.

Capture all required projection tokens together under the shared gates before reading. Recheck tokens for later batches. If a token moved, replay all accumulated approved bounded reads under the current READY projection gates and current access scope. Compare complete semantic results/coverage and relevant versions before continuing. Accept unchanged inputs and advance the request's validation tokens; do not mix changed earlier evidence with new reads. A changed or unprovable read set discards the request context and permits one whole-request retry within its existing deadline. The same retry budget is shared with access and live-verification retries.

## Final response publication

After an LLM/provider call, deterministic fallback or cache lookup, require every used projection READY and acquire its shared gate plus the access gate in the stated order. An active exclusive update or missing/DIRTY required projection returns `GRAPH_RECOVERY_REQUIRED`; scoped validation never bypasses recovery. Structural-only publication does not consult the INCIDENT gate.

A generation/snapshot difference alone is not answer invalidation. Replay the recorded graph reads when validation tokens changed, verify the complete read set and relevant mapping/effect/policy/access versions, and enforce the original expiry. Refresh relevant live Git heads before publishing commands or present-tense branch recommendations; a matching graph fingerprint cannot replace that check. If inputs remain equivalent, publish the existing explanation without another LLM call or consuming the retry. Preserve evidence's original snapshot/observation metadata and add `validated_against` projection tokens and `validated_at`; this does not refresh observations or extend TTL.

A relevant change discards the affected context/narrative and retries the whole request once. A second relevant change, or inability to prove equivalence after that retry while projections are READY, returns 503 `GRAPH_SNAPSHOT_CHANGED`. Dirty/unavailable projections use `GRAPH_RECOVERY_REQUIRED`. Relevant access changes retain the existing content-free access errors; stale live heads/expiry retain `STALE_EVIDENCE` and command-free historical explanations. Perform comparison, access validation and response admission together under short local gates; hold no gate across model or live-provider network calls. Subsequent provider work requires a new final validation.

## Clarification continuity

Sign or retain the opaque token's original `tenant_id`, `principal_id`, normalized `question_hash`, original/resolved `scope_hash`, clarification `kind`, `candidate_set_hash`, issued time and expiry. Default clarification TTL is 120 seconds, configurable. Candidate-set binding covers the original IDs/refs shown to the user; stored SHA labels are observations, not execution authorization. Global/projection generation and current mapping/effect/policy versions are not token-validity conditions. Verify the signed original binding, not a hash recomputed from today's candidate list.

Submission must match the original principal, question, scope, kind and exactly one member of the original candidate set. Reject tampering, cross-principal use and expired tokens using the existing 422/fresh-clarification behavior. Resolve the selected entity under current access, bindings and policy; do not auto-select a replacement. A removed/inaccessible candidate yields fresh permitted candidates or NOT_FOUND. Recompute the resumed decision from current graph reads and, for a branch, refreshed candidate/stable heads and complete ancestry/effect checks. Unrelated imports leave the selection usable; relevant changes may change the resulting decision or require clarification, without a token-generation reset loop. Selection never confirms an inferred association or reuses token-time commands.

## Required implementation evidence

- Continuous events are durably accepted, deduplicated and published in bounded windows; a continuous trickle cannot postpone the oldest window. Caps/backpressure and worker restart preserve every accepted event and the read interval.
- Incident batches do not mutate structural records/generation. Structural-only queries work during INCIDENT DIRTY; cross-projection reads refuse it. Interrupted incident recovery preserves structural and cross-projection identities.
- An unrelated incident/structural update during an LLM call preserves an identical read set and publishes with one LLM call. Changed inputs retry once; repeated relevant changes return the typed error.
- Added dependencies, negative-result matches, epic members, revision effects, policy changes, corrected deployments, document versions and access denials invalidate the appropriate answer even with unchanged cited node IDs/heads. Changed live heads/expiry still withhold commands and current recommendation prose.
- Clarification survives unrelated imports; candidate removal, permission loss, moved branch heads, expiry, question/scope/kind tampering and cross-principal submissions are handled without guessed scope.
- Execute the projection, read-set and batching cases through direct and MCP readers with the pinned database. Record actual latency, backlog, blocked-read fraction and retry counts. Documentation checks do not pass these runtime gates.
